### Bug #1: Sparse-Checkout Not Enforced - Manual kitty-specs/ Can Be Tracked

**Test**: test_manual_kitty_specs_creation_ignored
**Severity**: CRITICAL (data corruption risk, state divergence)
**Track**: Sparse-checkout infrastructure
**Found**: 2026-01-14
**Fixed**: Not yet fixed

**Symptoms**:
- User manually creates kitty-specs/ directory in worktree
- User can `git add kitty-specs/test.md`
- File shows in `git status --porcelain` as `?? kitty-specs/test.md`
- Sparse-checkout patterns NOT preventing tracking

**Root Cause**:
- Sparse-checkout patterns in .git/info/sparse-checkout not being enforced
- Pattern `!/kitty-specs/**` should prevent ANY files in kitty-specs/ from being tracked
- Git is ignoring sparse-checkout configuration or patterns incorrect

**Expected Behavior**:
- `git add kitty-specs/test.md` should be silently ignored
- `git status` should NOT show kitty-specs/ files (excluded by sparse-checkout)
- `git ls-files kitty-specs/` should return empty

**Actual Behavior**:
- Files CAN be added to git in worktree
- git status DOES show kitty-specs/ files
- Sparse-checkout not preventing user from committing worktree-local status

**Impact**:
- CRITICAL: Users could accidentally commit worktree-local kitty-specs/ changes to main branch
- This defeats the entire purpose of sparse-checkout (preventing state divergence)
- Multiple agents would have conflicting status files committed to main

**Fix Needed**:
- Location: ~/Code/spec-kitty/src/specify_cli/cli/commands/implement.py lines 596-642
- Investigate: Why sparse-checkout patterns not enforced?
- Validate: Test git config core.sparseCheckout, core.sparseCheckoutCone settings
- Validate: Test sparse-checkout file patterns format
- Consider: Maybe need `git sparse-checkout set` instead of manual file writing?

**Verification**:
- Test should pass after fix
- Manual `git add kitty-specs/` in worktree should be ignored
- Additional validation: Run `git sparse-checkout list` in worktree, verify patterns correct

**Files to Investigate**:
- ~/Code/spec-kitty/src/specify_cli/cli/commands/implement.py:596-642
- Check: How sparse-checkout file is written
- Check: How patterns are applied (git read-tree vs git sparse-checkout commands)

### Bug #2: Migration Script Not Working - kitty-specs/ Still in Old Worktree

**Test**: test_pre_sparse_checkout_worktree_migration
**Severity**: HIGH (upgrade path broken, user data at risk)
**Track**: Sparse-checkout infrastructure
**Found**: 2026-01-14
**Fixed**: Not yet fixed

**Symptoms**:
- Old worktree (created without sparse-checkout, simulating v0.11.0)
- Migration script runs: ~/Code/spec-kitty/fix-worktrees-to-sparse-checkout.sh
- Script exits with code 0 (success)
- BUT kitty-specs/ directory still present in old worktree
- Sparse-checkout not applied to existing worktree

**Root Cause**:
- Migration script not correctly applying sparse-checkout to existing worktrees
- Script might be setting config but not removing kitty-specs/ from working tree
- Need `git read-tree -mu HEAD` after configuring sparse-checkout

**Expected Behavior**:
- Migration script applies sparse-checkout to existing worktrees
- kitty-specs/ removed from worktree working directory
- git config core.sparseCheckout set to true
- Existing work preserved (only kitty-specs/ removed)

**Actual Behavior**:
- Script runs without error
- kitty-specs/ still present in worktree
- Sparse-checkout not actually applied to working tree

**Impact**:
- HIGH: Users upgrading from v0.11.0 to v0.12.0 have broken worktrees
- Old worktrees continue with divergent kitty-specs/ state
- Migration path not working - users stuck on v0.11.0

**Fix Needed**:
- Location: ~/Code/spec-kitty/fix-worktrees-to-sparse-checkout.sh
- Add: `git read-tree -mu HEAD` after setting up sparse-checkout
- Validate: kitty-specs/ actually removed from worktree after migration

**Verification**:
- Test should pass after fix
- Old worktree should have kitty-specs/ removed
- git config should show core.sparseCheckout=true

**Files to Fix**:
- ~/Code/spec-kitty/fix-worktrees-to-sparse-checkout.sh

### Bug #3: Symlink to kitty-specs/ Not Detected (DATA INTEGRITY CONCERN)

**Test**: test_symlink_kitty_specs_detected
**Severity**: MEDIUM (security concern, data integrity risk if user creates symlink)
**Track**: Sparse-checkout infrastructure
**Found**: 2026-01-14
**Fixed**: Not yet fixed

**Symptoms**:
- User creates symlink: `worktree/kitty-specs -> main_repo/kitty-specs`
- Symlink bypasses sparse-checkout isolation
- No detection or warning when running spec-kitty commands
- Additionally: `spec-kitty workflow` command doesn't exist (test tried to run it)

**Root Cause**:
- No symlink detection in spec-kitty commands
- Commands don't validate kitty-specs/ is a real exclusion (not symlink workaround)
- `spec-kitty workflow status` command doesn't exist in v0.11.0 (test issue)

**Expected Behavior**:
- Symlinks to kitty-specs/ detected and warned about
- OR symlinks detected and removed
- OR documentation that symlinks bypass sparse-checkout (known limitation)

**Actual Behavior**:
- Symlink silently present
- No detection, no warning
- User could modify main repo files thinking they're in worktree

**Impact**:
- MEDIUM: Unlikely scenario (user must manually create symlink)
- But if happens: Agent could corrupt main repo kitty-specs/ files
- Data integrity issue if symlink used as "workaround"

**Fix Options**:
1. Add symlink detection in workflow commands (check if kitty-specs/ is symlink, warn/error)
2. Document as known limitation with security warning
3. Add pre-commit hook to detect symlinks in worktrees

**Test Fix Needed**:
- Change test from using `spec-kitty workflow status` to a command that exists
- OR mark test as requiring v0.12.0+ if workflow command is new

**Files to Investigate**:
- What spec-kitty command can we use to test symlink detection?
- Should this be in implement.py when creating worktree?
- Or in tasks.py/workflow.py when running commands?
