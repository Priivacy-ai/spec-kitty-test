# Implementation Plan: Host-Based Agent Invocation

**Branch**: `005-host-based-agent-invocation` | **Date**: 2026-01-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/kitty-specs/005-host-based-agent-invocation/spec.md`

## Summary

Build the agent invocation infrastructure that enables the existing agentic E2E test framework (Feature 004) to actually execute real AI coding agents on the host machine. The framework already has comprehensive test scaffolding (paths, fixtures, fault injection, observability) - what's missing is the core mechanism to **invoke agents via subprocess** and **discover available agents at runtime**.

## Technical Context

**Language/Version**: Python 3.11+
**Primary Dependencies**: pytest, subprocess, shutil (stdlib)
**Storage**: File-based (git worktrees, log files)
**Testing**: pytest (existing `tests/agentic/` structure)
**Target Platform**: macOS/Linux host (no Docker for this feature)
**Project Type**: Single project - extension of existing spec-kitty
**Performance Goals**: Agent invocation completes within configured timeout (default: 30 minutes)
**Constraints**: Must not leave orphan processes; must capture all output; must work with existing fixtures
**Scale/Scope**: Support 5+ agent types (Claude Code, Copilot, Gemini, OpenCode, Codex)

## Key Design Decisions

### D1: Subprocess vs API

**Decision**: Use subprocess invocation, not SDK/API calls.
**Rationale**:
- Tests must validate the same CLI experience users have
- Avoids SDK version coupling
- Enables testing of CLI-specific behaviors (prompts, flags, output parsing)

### D2: Prompt Passing Strategy

**Decision**: Support three patterns per agent:
1. **stdin**: Pipe prompt to stdin
2. **file**: Write prompt to file, pass path as argument
3. **argument**: Pass prompt directly as CLI argument

**Rationale**: Different agents expect prompts differently.

### D3: Output Parsing

**Decision**: Agent-specific parsers with fallback to raw capture.
**Rationale**: Each agent has different output formats for success/failure/approval.

### D4: Worktree Isolation

**Decision**: Each test run gets its own git worktree.
**Rationale**:
- Prevents test interference
- Allows parallel execution
- Matches real user workflow (feature branches)

### D5: Process Cleanup

**Decision**: Use `atexit` handlers + explicit cleanup + signal handling.
**Rationale**: FR-013 requires no orphan processes.
