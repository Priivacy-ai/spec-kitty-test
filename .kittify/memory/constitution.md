## Project Mission

### Adversarial Testing Philosophy

We are an **adversarial testing project**. Our mission is to:

- Actively try to break Spec-Kitty in ways the implementors didn't imagine
- Protect end users from discovering bugs in production
- Find edge cases, race conditions, and unexpected behaviors
- Test real user experiences, not just code paths
- Test installation and upgrade paths
- Remember to test for Mac, Linux, Windows environments

### Separation of Concerns

**CRITICAL:** We NEVER edit the Spec-Kitty project itself.

- This test suite exists independently from the Spec-Kitty implementation
- When we find bugs, we **report them** by writing findings files
- The implementing team is responsible for fixing bugs in their codebase
- We love discovering bugs - they prove our testing is valuable

## Technical Standards

### Languages and Frameworks

- **Python 3.11+** minimum required
- **pytest** for test framework
- **Playwright** for browser/dashboard testing

### Testing Requirements

Dual testing strategy (no specific coverage target):

1. **Functional Tests** (`tests/functional/`)
   - Fast development iteration
   - Uses `SPEC_KITTY_TEMPLATE_ROOT` for local testing
   - Tests code correctness and features

2. **Distribution Tests** (`tests/distribution/`)
   - Real user experience validation
   - NO environment overrides
   - Tests package distribution correctness

**Principle:** *"Test what you ship, not just what you write."*

### Performance and Scale

Not a primary concern for this test suite.

### Platform Requirements

Unix-like systems only:
- Linux
- macOS

Windows support is not required.

## Findings Directory Canon

### Directory Structure

Findings are organized by **spec-kitty version** being tested:

```
findings/
├── 0.10.8/    - Findings for spec-kitty v0.10.8
├── 0.10.12/   - Findings for spec-kitty v0.10.12
├── 0.11.0/    - Findings for spec-kitty v0.11.0
└── TEMPLATE.md
```

### Rules

1. **Always use version directories** - The pattern is `findings/{version}/`
2. **Check version first** - Run `spec-kitty --version` before creating findings
3. **No topic-based directories** - Directories like `findings/test-infrastructure/` violate the pattern
4. **File naming** - Use `YYYY-MM-DD_NN_descriptive-name.md` format
5. **Follow the template** - See `findings/TEMPLATE.md` for required fields

### Invalid Examples

- `findings/test-infrastructure/` - topic, not version
- `findings/bugs/` - topic, not version
- `findings/dashboard/` - topic, not version

### Valid Examples

- `findings/0.11.0/2026-01-14_01_dashboard-crash-on-startup.md`
- `findings/0.12.0/2026-01-14_01_template-not-found-pypi.md`

## Governance

### Bug Reporting Process

We do NOT submit PRs to the Spec-Kitty project. Instead:

1. Write a findings file in `findings/{version}/`
2. Follow `findings/TEMPLATE.md` format
3. The project maintainer manually reports findings to the implementing team

### Amendment Process

Any contributor can propose amendments to this constitution by discussing with
the project maintainer.

### Compliance Validation

Contributors validate compliance during their work. Constitution violations
should be flagged and addressed before committing.
